# Generating PLC code from twin context

## Overview

The twin is the specification **for structure**: `_docs/context/` says what every device **is**,
what each functional group is **for**, and which safety conditions gate it. For **behaviour** — the
station handshake, interlocks, fault codes and recovery — the PLC is master, and the contract is
`_docs/reference/transport-behaviour.md`. This skill turns one functional group of that knowledge
base into a TwinCAT equipment module on the
[SPT framework](https://beckhoff-usa-community.github.io/SPT-Libraries/), wired to the twin over
EtherCAT.

Two projects, one solution at `Beckhoff/TwinCAT_1/PLC/`:

| Project | Port | Role | Who owns it |
|---|---|---|---|
| `SIM_1` | 852 | Twin device layer — OC_Core `FB_*` instances, ADS symbols Unity binds to | Generated by OC Assistant; only its `Mapping` actions are ours |
| `PLC_1` | 851 | **The control program** | This skill |

They meet at the process image: `PLC_1` drives real EtherCAT terminals, `SIM_1` sits behind
Beckhoff EtherCAT Simulation and mirrors them. Exactly like a real machine, which is the point.

**Read [reference.md](reference.md) before writing any ST.** It carries the SPT conventions, the
device mapping table, and the TcPOU XML mechanics. Do not generate from memory of the SPT docs — they
document **V4** while this project runs **V3.9**, and carry a few typos on top; third-party guides are
worse.

For the architecture behind those conventions, and the official build order that says to code Auto
mode **last**, read `Beckhoff/_docs/reference/spt-framework.md`. Split of authority: that page explains
*why*, `reference.md` is the authority on *what the identifiers actually are*.

## Start from the knowledge base

Read these, in order. Together they are the whole specification for one group, and none of them
needs Unity to be open:

```
_docs/context/PROVENANCE.md             the twin: how fresh, and was it verified live?
Beckhoff/_docs/context/PROVENANCE.md    the control side: how current is the type model?
_docs/context/fg-XX.md                  what the group IS - hierarchy, devices, authored prose
Beckhoff/_docs/context/fg-XX.md         what it BECOMES - control paths, SIM_1, PLC_1, mapping
_docs/reference/fg-XX-behaviour.md      the behaviour contract - sequences, faults, interlocks
```

**Structure lives in the main repo; realisation lives here.** The twin page states the twin PLC path;
only the Beckhoff page carries the control path *verified against the type model*, and only that one
works in a link or a binding.

**Gate on `PROVENANCE.md` before writing a line of ST.** If its export commit is older than the last
commit that touched the Unity scene, the digest describes a machine that has moved. Run
`refreshing-project-knowledge`, then start over. Generating from a stale digest produces symbols for
devices that moved or no longer exist, and nothing downstream will catch it.

If `PROVENANCE.md` says the digest was not verified against a live scene, that is workable — **say so
in your report**, because you could not prove it current.

## The symbols are already resolved

`fg-XX.md` lists the group's **real PLC symbols** in one table, with `oc.plcPath`, device type and
`FB_*` type. It lists devices that are *not* symbols separately, under "Not PLC symbols". Use the
first list; never generate code for the second.

That split is the three-key test, already applied: a node is a symbol when it has an
**`oc.deviceType`** and **neither `oc.aggregatedBy` nor `oc.simulationDevice`**. Every node carries
an `oc.plcPath`, including pure Unity grouping like `Laser Unit`, so **the path alone proves
nothing** — this is the single most common way to generate symbols that do not exist. Machine-wide
the test yields 83 of 180 nodes; FG_01 yields 5 of 5.

- `oc.aggregatedBy` — a `PanelSampler` folded this device into its own symbol. The panel is one
  symbol; its buttons and lamps are bits inside it, not devices of their own.
- `oc.simulationDevice` — the device talks to no PLC at all. It exists for the simulation.

The digest is already cross-checked against each scene's `_Project_Tree.xml` — `build_knowledge.py` refuses
to write when the two disagree, so a digest that exists is a digest whose symbol list both exports
agree on. Fall back to the raw `Unity/Assets/StreamingAssets/<Scene>_Context.json` only for something
the digest genuinely does not carry, and never read the scene YAML.

## Derive, never invent

Inherited verbatim from `authoring-context-nodes`: **never invent the why.**

What you may read: device types and I/O from the symbol table and the OC_Core FB layouts; the cycle
from the group's `Process` section; permissives from its `Safety` section; the group-level handshake
from `Interfaces`.

**The station handshake comes from `_docs/reference/transport-behaviour.md`, not from the MIL.**
The `Preliy.Demo` scripts under `Unity/Assets/Demo_1/Scripts/MIL/` are the twin's animation and
implement the older contract — no transfer latch, no level check before a lift runs its carriage
belt, no reset path — so copying them reproduces bugs that are already fixed. They remain useful for
the *shape* of a group's own cycle and for its timings; read them for that.

What you may not do: fill a gap with plausible automation logic. `fg-XX.md` marks its gaps
explicitly — an "Undocumented" list, and a "_No authored context_" note where a group was never
documented. **Those are gaps, not permission to infer.** A step with no grounding in the digest or
the MIL script gets a `// TODO` and a question to the user. Invented interlocks are worse than
missing ones, because they will be believed.

When the twin's authored context and the PLC disagree **about behaviour**, the PLC wins — say so, and
add it to the correction register in `transport-behaviour.md` so the twin gets fixed later. There is
already precedent: nine authored `Function` entries state the stopper polarity backwards.

When they disagree about **structure** — a device, a path, a device type — the twin wins and the PLC
is out of date. When the digest and the MIL disagree and no PLC code exists yet, say so and ask. Do
not silently pick one.

## Structure of what you generate

```
PLC_1/
├── POUs/MAIN.TcPOU                  Machine instance + init guard + commissioning commands
├── DUTs/ST_HMI_<GROUP>*.TcDUT       the group's HMI contract (Command/Config/Status)
└── Modules/
    ├── 00 Machine/Machine.TcPOU     EXTENDS FB_PackML_BaseModule, registers the groups
    └── NN <GROUP>/<GROUP>.TcPOU     EXTENDS FB_PackML_BaseModule, one per functional group
```

**There is no I/O GVL.** Every device is an SPT component that owns its own process-image
variables — `FB_DigitalSensor` declares `HardwareInput AT %I*`, `FB_SingleSolenoidFeedback`
declares `_ExtendOutput AT %Q*`. Only a signal with no component that fits (a bare coil) gets
its own `AT %Q*` in the module, as `FG_01._LaserFire` does.

One equipment module per functional group, named exactly as the group (`FG_01`), so the control
program's tree matches the twin's PLC tree matches the Unity hierarchy. That correspondence is the
whole value of the pipeline — do not rename things on the way through.

Keep all component↔process-image wiring in two actions on the module, `ReadInputs` and
`WriteOutputs`, called around `SUPER^.CyclicLogic()`. Sequence logic then touches only the abstract
component API (`.Extend()`, `.Extended`), never a `%I*` variable. Beyond being the SPT layering rule,
this isolates the one part that depends on exact SPT library property names into a block you can fix
in one place.

## Publish the module to the HMI

Every module ends with a struct the panel can bind:

```pascal
	// --- HMI ----------------------------------------------------------------
	// One struct for the whole group. Filled by PublishStatus after the base has run,
	// so every field is this scan's value.
	{ attribute 'TcHmiSymbol.AddSymbol' }
	HMI	: ST_HMI_<GROUP>;
```

The pragma makes the HMI server publish and label the symbol by itself — **the comment above
the declaration becomes the label**. Declare the DUT triple
`ST_HMI_<GROUP>_{Command,Config,Status}` plus the aggregating `ST_HMI_<GROUP>`, register all
four in `PLC_1.plcproj`, and fill the struct from a `PublishStatus` action called after
`SUPER^.CyclicLogic()` — so `_CurrentState` and the permissives are this scan's values.

Declaring the struct is not filling it. A published struct nobody writes is a live ADS symbol
that reads zeros forever. See `building-hmi-elements`.

## Link the module's I/O

Hand off to `mapping-plc-io`. Two things to know before you write a pragma:

- A **member-path** `TcLinkTo` (`.Member := ...`) resolves on a STRUCT/DUT variable and **not**
  on a FUNCTION_BLOCK instance. On an FB instance the compiler accepts it, reports nothing and
  links nothing. A **single-target** pragma resolves on any plain located `AT %I*` / `AT %Q*`
  scalar. Anything inside a reusable unit block is linked from `Mapping_PLC.xml` instead.
- A unit block instantiated more than once cannot carry per-instance channels in a pragma at
  all — the pragma is on the type.

## Wire the twin to match

`SIM_1/<GROUP>/<GROUP>.TcPOU` → the `Mapping` action maps twin FB members to
`GVL_EtherCAT_1_SIM.<terminal>.bIn*/bOut*`. `GVL_EtherCAT_1_SIM` already declares every
terminal with bulk pragmas, so it normally needs no edit.

**Only `Mapping` changes.** The `{region generated code}` declaration block belongs to OC
Assistant; editing it will be overwritten on the next twin regeneration.

Legacy `GVL_PLC.Inputs.Ixxx.b` byte addressing is what you are replacing. It survives only in
the parked template under `Siemens/TIA_1/`, not here.

## Register everything

A generated file that is not in the `.plcproj` does not exist as far as TwinCAT is concerned, and
this fails silently. For every new file add both:

```xml
<Compile Include="Modules\01 FG_01\FG_01.TcPOU"><SubType>Code</SubType></Compile>
<Folder Include="Modules\01 FG_01" />
```

Copy the exact formatting from `SIM_1/SIM_1.plcproj`.

## Verify before reporting

Nothing here compiles without TwinCAT, so prove what you can:

```bash
# every generated file parses, and every Id GUID is unique across the project
python -c "
import glob,re,xml.etree.ElementTree as ET,collections
ids=collections.Counter()
for f in glob.glob('Beckhoff/TwinCAT_1/PLC/**/*.Tc*', recursive=True):
    ET.parse(f)
    ids.update(re.findall(r'Id=\"(\{[^}]+\})\"', open(f,encoding='utf-8-sig').read()))
print('dupes:', [i for i,c in ids.items() if c>1])"
```

**Then cross-check every library call against the installed symbol tree.** For each declared
component, collect `<instance>.<member>` from the generated ST and assert each member exists in that
FB's `browsercache` node set, walking the inheritance chain
(`FB_SingleSolenoidFeedback` → `FB_SingleSolenoid` → `FB_ComponentBase`). This is cheap, it is a real
check rather than a guess, and it catches wrong property names — including the ones the SPT
documentation gets wrong — before a build cycle is spent on them. Strip comments first.

Also assert no V4 enum literal survives: every `E_PMLState.` / `E_PMLCommand.` / `E_PMLUnitMode.`
must be followed by `ePML`.

Then diff the generated sequence step by step against the MIL script.

Finally, rebuild `PLC_1` in XAE and run:

```bash
python Beckhoff/_private/tools/plc_io.py build           # refuses on a stale .tmc or a wiring that does not add up
python Beckhoff/_private/tools/build_plc_knowledge.py   # rebuild this module's group pages
python Beckhoff/_private/tools/hmi_check.py             # every binding still resolves
```

Then read your group's own Beckhoff page back. Its **PLC_1** section shows the module registered, the
PackML states implemented and the fault codes found; **Components** gives `I/O` and `Linked` per
device. Anything where `Linked` is short of `I/O` is unfinished work, and `plc_io.py reconcile`
names the signals.

Report: devices covered, signals assigned, what you could not verify, whether `PROVENANCE.md` was
live-verified, and every `// TODO` you left.

## Common mistakes

- **Working from a stale digest.** Check `PROVENANCE.md` first. It costs one `Read`.
- **Treating `oc.plcPath` as proof of a symbol.** Every node has one. Use the three-key test — or
  just use the split `fg-XX.md` already made.
- **Generating a symbol for an aggregated device.** The 10 `oc.aggregatedBy` devices are bits inside
  a panel's `FB_Panel`, not devices.
- **Editing the `{region generated code}` block in `SIM_1`.** OC Assistant owns it.
- **Forgetting the `.plcproj` entry.** The file will simply not be in the project.
- **Reusing a GUID.** Every POU, method, action, property, getter and setter needs a fresh one.
- **Calling `StateComplete()` in `Execute`.** `Execute` is the one acting state that does not
  self-complete; it needs an explicit `Complete` command.
